# Alfa Global CBDC Hub

Личный кабинет юридического лица для сопровождения внешнеэкономических сделок
от начала до завершения: финансовая сторона, документооборот, регуляторные
проверки, статус исполнения.

Этот репозиторий (`IVR-CBDC/Frontend`) — фронтенд-часть системы: BFF (Node.js)
и SPA (React). Бэкенд — отдельный репозиторий (`IVR-CBDC/Backend`, локально
`/home/legors/Documents/IVR`): три сервиса на C++/Drogon и Python/FastAPI за
Traefik, каждый со своей Postgres, плюс общий Redis. BFF — единственная дверь
из SPA в этот бэкенд: держит сессию пользователя в HttpOnly-cookie, ходит в
сервисы с его JWT и раздаёт события сделок через WebSocket.

## Структура репозитория

```
alfa-cbdc-hub/
├── bff/         BFF-слой (Node.js + Express + WebSocket)
├── frontend/    Клиентское SPA (React + TypeScript + Vite, с поддержкой PWA)
└── e2e/         Сквозные тесты (Playwright) — против уже поднятого стенда
```

## BFF

Агрегирует данные, реализует бизнес-логику для UI, кеширование и сервис
уведомлений в реальном времени через WebSocket. Реализация — поверх реальных
сервисов Backend-репозитория (auth/core/commission), моков не осталось.

Две ручки здоровья (F10, final review): `GET /health` — только живость
процесса, без сети (`{"ok":true}`), для liveness-проверок. `GET /ready` —
настоящая готовность: Redis-подписка в моменте (не "когда-то подписались")
плюс достижимость auth/core/commission, с коротким TTL-кешем, чтобы частый
healthcheck не заваливал апстримы запросами. Именно `/ready` проверяет
compose Backend-репозитория.

### Локальный запуск против стенда Backend

Сначала подними стенд Backend (`docker compose ... up -d --wait`, см. README
того репозитория) — BFF ничего не эмулирует и падает при старте, если не
может достучаться до обязательных переменных окружения:

```bash
cd bff
pnpm install
AUTH_URL=http://127.0.0.1:18080 \
CORE_URL=http://127.0.0.1:18081 \
COMMISSION_URL=http://127.0.0.1:<host-порт commission, если он проброшен> \
REDIS_URL=redis://127.0.0.1:<host-порт redis, если он проброшен> \
ALLOWED_ORIGINS=http://localhost:5173 \
pnpm dev         # http://localhost:4000, WS: ws://localhost:4000/ws
```

`service-commission` и `redis` в dev-оверлее Backend порт наружу не
публикуют (см. README Backend-репозитория) — если он нужен с хоста, это
отдельная правка того репозитория, не этой задачи. Внутри общего
docker-сетевого стенда (см. ниже, Task 5 плана 05) BFF обращается к ним по
именам сервисов (`http://service-commission:8000`, `redis://redis:6379`),
не по host-портам.

Обязательные переменные (без них процесс падает при старте с понятным
сообщением, см. `bff/src/config.ts`):

| Переменная | Назначение |
|---|---|
| `AUTH_URL` | адрес service-auth (регистрация/логин/JWKS) |
| `CORE_URL` | адрес service-core (сделки, документы, трекинг) |
| `COMMISSION_URL` | адрес service-commission (котировки сценариев) |
| `REDIS_URL` | адрес Redis (подписка на события сделок) |
| `ALLOWED_ORIGINS` | список Origin через запятую — проверка CSRF на мутирующих запросах |

Необязательные: `PORT` (по умолчанию 4000), `COOKIE_SECURE` (`true`/`false`,
по умолчанию `false` — включай в проде за HTTPS), `UPSTREAM_TIMEOUT_MS`
(по умолчанию 5000).

```bash
pnpm test        # vitest, без поднятого стенда — upstream'ы подменены
pnpm typecheck
pnpm build       # -> bff/dist
```

### Контракт для SPA (F8, final review)

Единственный источник правды по формам — `bff/src/types.ts` (типы кадров WS
и доменных сущностей). Здесь — то, что план 06 не найдёт просто прочитав
типы: смысл кодов закрытия и правило перезапроса.

**HTTP-ошибки.** Единый конверт `{code, error}` на всех ответах (`error` —
русский текст для показа пользователю, `code` — то, по чему ветвится SPA).
Словарь кодов:

| code | статус | значит |
|---|---|---|
| `VALIDATION_ERROR` | 400 | битый JSON, нечисловой `limit`, невалидное тело запроса — вход не дошёл до апстрима |
| `UNAUTHORIZED` | 401 | нет cookie сессии вовсе — на логин |
| `TOKEN_EXPIRED` / `INVALID_TOKEN` | 401 | апстрим отверг токен из cookie — BFF уже погасил cookie (`Set-Cookie` с истёкшей датой, F5), SPA просто ведёт на логин |
| `FORBIDDEN_ORIGIN` | 403 | мутирующий запрос с недопустимым/отсутствующим `Origin` |
| `NOT_FOUND` | 404 | неизвестный маршрут — в т.ч. под `/api/*` (F4) |
| код апстрима как есть (напр. `VERSION_CONFLICT`) | как у апстрима | бизнес-ошибка core/commission, BFF её не переинтерпретирует |
| `UPSTREAM_CONTRACT_VIOLATION` | 502 | апстрим ответил, но нарушил контракт (напр. auth вернул токен без `exp`) — не значит "сервис недоступен" (F9) |
| `UPSTREAM_UNAVAILABLE` | 503 | апстрим не ответил вовсе (таймаут/сеть/5xx) |
| `INTERNAL_ERROR` | 500 | сбой в самом BFF |

**WebSocket (`ws://.../ws`).** Кадры сервера (тип `WsServerFrame` в
`types.ts`):

- `{"type":"connection.ack"}` — первый кадр после успешной аутентификации
  сокета, при каждом (пере)подключении.
- `{"type":"heartbeat","at":"<ISO8601>"}` — раз в ~25с, подтверждает, что
  прикладной канал жив (отдельно от протокольных ws ping/pong, которыми
  сервер обнаруживает мёртвые сокеты, F6 — SPA их не видит).
- `DealEvent` (`{"type":"deal.updated"|"deal.created"|"notification.created","seq":number,"dealId"?,"notificationId"?,"at"}`)
  — **триггер, не носитель данных**. У pub/sub нет истории (спека §4.4):
  событие говорит "что-то изменилось", а не "вот новые данные" — экран
  перезапрашивается заново тем же REST-эндпоинтом, что и при обычной загрузке.

**Правило перезапроса.** На каждый `connection.ack`, включая переподключения
после разрыва, SPA обязана перезапросить текущий экран. Между разрывом и
переподключением события теряются безвозвратно (истории у pub/sub нет) —
`connection.ack` единственный сигнал "возможно, вы что-то пропустили".
`DealEvent` во время активного соединения — тоже сигнал перезапросить
затронутый экран, не патчить состояние из полей события.

**Origin при апгрейде** (F2, final review, round 2): недопустимый/отсутствующий
`Origin` отклоняется **на самом HTTP-апгрейде**, через `verifyClient` —
сервер отвечает `403` и рвёт TCP-соединение, WebSocket-хендшейк до `101
Switching Protocols` не доходит вовсе. Раньше эта проверка жила в
обработчике `"connection"` (уже после успешного апгрейда) и сокет сперва
открывался, а потом закрывался прикладным кодом — тот самый "accept first,
close later", который и был дырой (страница с чужого origin получала
открытый, пусть и на мгновение, сокет). С `verifyClient` этого окна больше
нет: страница с недопустимого origin вообще не видит успешного хендшейка —
клиентский WebSocket получает ошибку/`unexpected-response`, а не `open`.
Раз апгрейд отклоняется до хендшейка, нести прикладной код закрытия
(4000-4999) здесь уже нечему — **4403 для Origin больше не применяется**.

**Коды закрытия WS** (диапазон 4000-4999 — прикладные, не протокольные;
применимы только после успешного хендшейка):

| код | значит | что делать SPA |
|---|---|---|
| `4401` | хендшейк уже состоялся (Origin был допустимый), но нет cookie сессии или токен недействителен | как HTTP 401 — на логин |

### Продовый образ

```bash
docker build -t bff:local -f bff/Dockerfile bff
```

Многостадийная сборка (`node:22-alpine`): зависимости → `tsc` → рантайм
только с `dist/`, прод-зависимостями и непривилегированным пользователем.
`HEALTHCHECK` в образе не задан — он определяется в compose Backend-репозитория
(так принято в этом стенде, см. `docker-compose.yml` там же), который умеет
поднимать `bff` либо из готового образа, либо собрать его отсюда через
`docker-compose.override.yml.example`.

## Frontend (SPA)

React-приложение на TypeScript, собирается в статические файлы (HTML/JS/CSS),
поддерживает установку как PWA и push-уведомления через service worker.

```bash
cd frontend
npm install
npm run dev      # http://localhost:5173, проксирует /api и /ws на backend
```

Прокси Vite должен указывать на BFF: `pnpm dev` в `bff/` (см. выше) слушает
`http://localhost:4000`; при запуске BFF внутри стенда Backend через
`docker-compose.dev.yml` тот же BFF доступен с хоста на
`http://127.0.0.1:14000` (F12, final review — порт проброшен только этим
dev-оверлеем, см. README Backend-репозитория). Оба варианта — один и тот же
BFF, разница только в том, кто его поднял.

Экраны (см. `src/components`):

1. **Dashboard** — список активных сделок, этапы, индикаторы проблемных мест.
2. **CreateDeal** — многошаговый мастер: страна → тип операции → сумма/валюта → контрагент.
3. **ScenarioSelection** — карточки сценариев расчёта (ЦВЦБ / банковский перевод / смарт-контракт / торговое финансирование).
4. **Documents** — статус каждого документа с пояснением, зачем он нужен.
5. **Tracking** — ключевой экран: полный таймлайн, участники, статус, причины задержек.

### Продовый образ (план 06)

```bash
docker build -t frontend:local -f frontend/Dockerfile frontend
```

Многостадийная сборка (`node:22-alpine` → `pnpm build` → `nginx:alpine`):
статика собирается тем же `pnpm build`, что и локально, и раздаётся nginx'ом
(`frontend/nginx.conf`) — тем же образом для любого хоста. Конфиг решает две
вещи, без которых SPA либо не открывается по прямой ссылке, либо тихо не
получает живые обновления:

- fallback на `index.html` для всех путей, не совпавших с файлом на диске —
  иначе прямая ссылка на внутренний маршрут (`/deals/:id/tracking`) даёт
  404 у nginx, хотя роутинг на самом деле клиентский (react-router-dom);
- `/api` и `/ws` проксируются на `bff:4000` (имя сервиса в общей
  docker-сети Backend-репозитория), причём `/ws` — с заголовками
  `Upgrade`/`Connection: upgrade`, иначе апгрейд до WebSocket не проходит
  и живые обновления сделок молча не подключаются (внешне приложение
  выглядит рабочим, просто никогда не обновляется само).

`HEALTHCHECK` в образе не задан — как и у BFF, он определяется в compose
Backend-репозитория (см. README того репозитория, раздел «Frontend SPA»),
который поднимает `frontend` под своим профилем, потому что сам образ
(`ghcr.io/ivr-cbdc/frontend/spa`) CI этого репозитория ещё не публикует.

## E2E (Playwright)

`e2e/` — сквозные тесты на Playwright (только chromium), проверяющие
критерий готовности системы целиком: регистрация, сделка, сценарий расчёта,
документооборот и трекинг до `completed` — на настоящем стенде (SPA + BFF +
Backend-сервисы), без моков. Пакет самостоятельный (не workspace-член
`bff`/`frontend`) и не поднимает стенд сам — стенд живёт в
Backend-репозитории и запускается снаружи; `playwright.config.ts` при старте
(`globalSetup`) только проверяет, что SPA и BFF уже отвечают, и падает с
понятным сообщением, если нет.

Тестам обязательно нужен ручной режим эмулятора Backend-репозитория
(`EMULATOR_MANUAL=true`) — иначе прогресс сделки (проверка документов,
комплаенс, расчёт) решает время, а не тест, и `POST /internal/emulator/tick`
отвечает `404`.

F8 (final review): единственный поддерживаемый способ поднять стенд под
e2e — `make e2e-stand-up` в Backend-репозитории (см. его README, раздел
«Стенд под e2e»); он зашивает `EMULATOR_MANUAL=true` в саму цель, а не
полагается на то, что вызывающий её не забудет переменную окружения:

```bash
cd /home/legors/Documents/IVR
make e2e-stand-up
# если стенд уже был поднят с EMULATOR_MANUAL=false — пересоздать только service-core:
EMULATOR_MANUAL=true docker compose -f docker-compose.yml -f docker-compose.dev.yml \
  up -d --wait service-core
```

```bash
cd e2e
pnpm install
pnpm exec playwright install --with-deps chromium   # один раз; --with-deps требует sudo —
                                                      # если недоступен, подойдёт install без него,
                                                      # если системные зависимости Chromium уже стоят
pnpm test        # прогон против уже поднятого стенда, один воркер (стенд общий)
pnpm test:ui     # интерактивная отладка (Playwright UI)
```

Переменные окружения (не обязательны — значения по умолчанию рассчитаны на
локальный стенд из README Backend-репозитория):

| Переменная | По умолчанию | Зачем |
|---|---|---|
| `E2E_BASE_URL` | `http://127.0.0.1:8090` | SPA. Он же адрес BFF — см. ниже. |
| `E2E_BFF_URL` | *совпадает с `E2E_BASE_URL`* | Рычаг для нестандартного стенда (BFF за отдельным доменом). В обычном прогоне задавать не нужно. |
| `E2E_CORE_URL` | `http://127.0.0.1:18081` | service-core, только для `POST /internal/emulator/tick`. |
| `E2E_SKIP_EMULATOR_CHECK` | не задана | `=1` отключает проверку режима эмулятора в `global-setup` (см. ниже). Аварийный рычаг. |

**Адрес один (план 08).** nginx образа SPA проксирует `/api` и `/ws` на BFF
(`frontend/nginx.conf`) — тем же путём, которым в BFF ходит настоящий
браузер. Поэтому запросы, которые фикстуры шлют мимо браузера, идут туда же,
а не в отдельный host-порт BFF. Выигрыш не в удобстве: `Origin` теперь
совпадает с адресом страницы **по построению**, а не потому, что кто-то не
забыл выставить две переменные согласованно (BFF проверяет `Origin` на CSRF,
см. «Контракт для SPA», `FORBIDDEN_ORIGIN`). И прогон проверяет тот самый
периметр, который видит пользователь: план 08 убрал наружу всё, кроме
`frontend` и `bff`, а e2e, ходившие в BFF напрямую, эту границу обходили бы.

`E2E_CORE_URL` остаётся особым случаем и останется им: ручка тика
внутренняя, наружу не публикуется ни в compose, ни в k3s (спека §4.3,
Backend). Отсюда и записанное в спеку решение: **e2e живут на
compose-стенде и не являются частью проверки кластерного деплоя** — её
делают `helm lint`/`helm template`, пробы `/health` и `/ready` и smoke-цели
`make k3s-test-*` Backend-репозитория.

**Проверка стенда до первого теста.** `global-setup.ts` проверяет три вещи и
падает одной понятной строкой, а не таймаутом посреди прогона: SPA отвечает;
BFF отвечает **через** `/api` фронта (`/api/auth/me` без сессии обязан дать
401 — 200 с HTML значит, что прокси не настроен и nginx отдал `index.html`);
service-core поднят в ручном режиме эмулятора (`emulator_manual: true` в его
`/health`). Последнее — лечение ловушки плана 07: при автоматическом режиме
ручка `/internal/emulator/tick` не регистрируется вовсе, и единственным
симптомом был `404` в середине теста, неотличимый от опечатки в пути.

Каждый тест регистрирует свою компанию через API BFF (`fixtures/stand.ts`,
фикстура `company`) — уникальный логин и ИНН на тест, общих фикстур с
данными нет, тесты не зависят друг от друга и от порядка запуска. Прогресс
сделки тесты двигают сами через `tick()` (`POST /internal/emulator/tick`) и
проверяют автоожидающими `expect(...)`/`expect.poll(...)` — без
`waitForTimeout`/`sleep`.

**F8 (final review, явно, а не молчанием):** первое слово критерия
готовности (§1 спеки — «пользователь юрлица логинится...») сквозным тестом
не закрыто в части самой формы регистрации: `company` заводится через
прямой POST на `/api/auth/register`, а не через экран `/register`. Решение
осознанное — скорость и надёжность подготовки данных важнее для остального
набора, чем ещё один прогон формы, и путь входа (`/login`, в т.ч. с неверным
паролем) e2e покрывает отдельно (`session.spec.ts`). Но сама форма
регистрации сейчас не проверена ни одним e2e-тестом — это открытый пробел,
а не забытый шаг.

## CI (план 07, задача 3)

`.github/workflows/ci.yml` — на каждый `pull_request` и `push` в любую ветку
кроме `main` (тот же паттерн, что у Backend-репозитория), три независимые
джобы:

- `bff` — `pnpm --dir bff install --frozen-lockfile`, `typecheck`, `test`
  (vitest, upstream'ы подменены), `build`.
- `frontend` — то же самое для `frontend` (vitest + jsdom, без сети).
- `e2e` — чекаутит Backend-репозиторий (`IVR-CBDC/Backend`, путь `backend`,
  без `ref:` — т.е. его ветку по умолчанию), собирает образы `bff`/`frontend`
  из этого чекаута, **тянет** backend-образы из ghcr, поднимает стенд
  Backend-репозитория (`make e2e-stand-up` там же, см. README
  Backend-репозитория) и гоняет Playwright (`e2e/`) против него; при падении
  трассировки/отчёт Playwright и `docker compose logs` уходят в артефакт
  джобы.

  **Backend-образы больше не собираются здесь (план 08, долг плана 07).**
  Раньше каждый PR этого репозитория собирал C++ трёх чужих сервисов полным
  `cmake` поверх drogon — на холодном раннере десятки минут, и при этом не
  проверял ничего: код Backend в таком PR не менялся. Теперь джоба делает
  `docker pull ghcr.io/ivr-cbdc/backend/{service-auth,service-core,service-commission}:main`
  и поднимает стенд без `--build` (`E2E_BUILD=` + `SERVICE_*_IMAGE`, оба
  рычага заведены в Backend плана 08). Тег плавающий (`:main`) намеренно:
  sha коммита Backend этому прогону неизвестен и узнать его неоткуда. Для
  **выката** плавающий тег запрещён — там `sha-<7>`, см. ниже.

  **Порядок мержа (F2, final review):** `make e2e-stand-up` существует
  только в ветке `feat/e2e-support` Backend-репозитория, не в его ветке по
  умолчанию — эта джоба не может пройти, пока `feat/e2e-support` не влита в
  default branch Backend. Preflight-шаг `make -n e2e-stand-up` в
  `ci.yml` ловит рассинхрон явным сообщением, а не голым «No rule to make
  target».

## Публикация образов и связь с деплоем (план 08)

`.github/workflows/publish.yml` — на `push` в `main` (и вручную через
`workflow_dispatch`): собирает и пушит `ghcr.io/ivr-cbdc/frontend/bff` и
`ghcr.io/ivr-cbdc/frontend/spa` двумя тегами — `sha-<7>` и плавающим `main`
— и затем шлёт `repository_dispatch` в `IVR-CBDC/Backend`.

Зачем dispatch вообще. Деплой живёт в Backend-репозитории: один цикл
`helm upgrade` по `infra/services.tsv` на пять релизов. Три образа
собираются там и тегируются sha **его** коммита; `bff` и `spa` собираются
здесь, и sha этого коммита Backend неоткуда не известен. Dispatch кладёт
теги в `Backend/infra/helm/frontend-tags.env` коммитом бота — так ответ на
вопрос «что сейчас на стенде» остаётся в git, а не в состоянии реестра.

Почему в dispatch уезжает `sha-<7>`, а не `latest`/`main`. `helm upgrade` с
неизменившимся `image.tag` — no-op: kubelet не пойдёт за новым образом,
релиз обновится «успешно», и новая сборка фронта молча не выкатится.
Плавающий тег там хуже пустого, и `Backend/infra/k3s-preflight.sh` его
отвергает явным сообщением. Плавающий `:main` публикуется для другого
потребителя — чужого CI (как и мы тянем backend-образы по `:main`).

Что нужно завести, когда у репозиториев появится remote:

| Секрет | Где | Зачем |
|---|---|---|
| `BACKEND_DISPATCH_TOKEN` | этот репозиторий | PAT с `contents: write` на `IVR-CBDC/Backend`. `GITHUB_TOKEN` не подходит принципиально — он ограничен своим репозиторием. |
| `GHCR_READ_TOKEN` | этот репозиторий | PAT с `read:packages`, если пакеты Backend приватные. Для публичных не нужен. |

**Честно:** ни `publish.yml`, ни джоба `e2e` здесь не выполнялись и
выполниться не могут — у репозиториев нет remote, организации `IVR-CBDC` на
GitHub не существует, ни один образ не опубликован. Оба файла проверены
разбором YAML и сверкой контракта с принимающей стороной
(`Backend/.github/workflows/frontend-tags.yml`).

**Честно (не подлежит обсуждению):** ни у одного из двух репозиториев сейчас
нет git remote, и ни один образ никуда не опубликован — шаг `actions/checkout`
с `repository: IVR-CBDC/Backend` в джобе `e2e` обращается к реальному
GitHub-репозиторию по имени, которого не существует. Джоба `e2e` **не
выполнялась и не проходила на раннере GitHub Actions** — она написана и
проверена локально: YAML разобран парсером (`python3 -c "import yaml; ..."`),
`bash -n` прогнан по всем встроенным скриптам шагов, а сами шаги (сборка
образов bff/frontend, `gen-keys.sh`, подъём стенда через
`docker compose ... --profile bff --profile frontend up -d --build --wait`,
`pnpm test` в `e2e/`) воспроизведены вручную на этой машине против настоящего
поднятого стенда — все 4 спеки проходят дважды подряд (см. отчёт
плана 07, задача 3). Джобы `bff` и `frontend` воспроизведены точно так же и
тоже не запускались на реальном раннере GitHub Actions — раннер CI не
проверен, только локальное воспроизведение его шагов.
